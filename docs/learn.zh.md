# 这个定价引擎到底在做什么？

设想你负责一个商品，现在想知道下次该报什么价格。系统不是把几个报价简单平均，而是先判断哪些价格允许，再比较每个价格可能发生的结果。

## 先试三件事

1. 选一个“低频销售”商品，点击比较价格。左边是真实历史记录；中间的成本、毛利要求和弹性是你设置的假设；右边是计算。
2. 点“试一下：成本和售价上限冲突”。例如成本要求你至少卖 120，但规则最多允许卖 112，系统应该说需要人处理，不能硬给一个看起来合理的答案。
3. 选“最近没有销售记录”的商品。系统会让你先检查库存、是否已下架等，不能假造一件销量后声称有利润提升机会。

## 长尾的关键：信息少时，不能假装很精确

一年卖几次的零件很难独立估计“涨价以后少卖多少”。一个可研究的办法是借用功能、适配车型、品牌、替代性等相近商品的信息，等这个商品有更多证据后，再逐步增加自身信息的权重。

页面展示的是这个思想的**教学计算**：你设置单品信号和同类经验，系统按有销量周数给权重。这个权重不是训练出来的，UCI 数据也没有正式零件分类。下一步才是用适合的数据检验分组与层级模型，不能将教学公式写成已实现的统计结论。

## 为什么不是把成本价、竞品价、模型价平均？

这些数字的职责不同：成本及最低毛利是底线；合同或调价幅度可能是硬限制；竞争价格可以是参考，也可以是业务规定的上限；需求响应影响不同价格下可能卖出的数量。

如果规则冲突，平均值并不能解决问题。必须把冲突交给负责的人，决定是成本数据有问题，还是应改变某条业务规则。

## 怎么从范围变成一个候选价？

系统在允许范围内试一批价格。每个价都按三种价格敏感度假设算销量，再算 `(价格－假设单位成本)×情景销量`。最后选择三种情景中最差毛利仍相对最高的候选价。

这是帮助你比较取舍的情景分析，不是保证涨价后真的能多赚。当前销量基准也只是历史 8 周均值，不是经过验证的需求预测。真实工作需要核实成本和可售状态、估计响应关系、让业务人员审核，再用适当的对照实验验证。

## Agent 放在哪里？

当前第一版没有 Agent 或大语言模型。定价的计算与规则已经可以直接运行。

以后可以让 Agent 帮你找该商品的证据、调用定价工具、解释冲突、准备审核材料。它读的是已算出的价格和理由，不能随口编造成本、弹性或直接越过定价限制。

## 面试里可以怎么说？

> I built a small independent pricing workbench to make the decision process visible. It uses public historical retail transactions, with costs and elasticities clearly labeled as scenario assumptions. It checks business constraints, compares contribution-profit scenarios, and records a local human review. The next modeling step is to estimate and validate price response; I am not claiming a production parts-pricing system or a measured profit uplift.

中文记忆：**真实销量 → 假设透明 → 先检查规则 → 再比较价格 → 审核与实验。**
