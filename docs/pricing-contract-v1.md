# Pricing contract v1 — Phase 3 design

Prepared 2026-11-18. The bounded local Phase 3 engine now implements these interfaces; see the [engine handoff](pricing-phase3-engine-handoff.md) for concrete schemas, tests, real inference timing and remaining integration gates. Independent Phase 3 promotion, authenticated workflow and hosted availability remain separate. No model fitting, protected-label access, bundle export, or runtime change is authorized by this document. This complements the [interface design](design-v2.md), [backend contract](backend-contract-v1.md), [weekly input contract](data-contracts/weekly-pricing-v1.md), and [active model protocol](model-protocol-v2.md). ## Scope and meaning

The first comparison covers every origin-visible series for exactly four weeks. The reference scope is **249 store–brand series**, cutoff 160, source weeks 161–164; these are not 249 distinct products or calendar dates. Comparison admission is **≤300 series**, distinct from the import limit of **≤2,000 series**; larger imports remain inspect-only until a supported comparison path exists and are never silently truncated. One row per admitted scope member survives missing data, model fallback, rule conflict, exclusion, and all-hold outcomes. An independent never-sold catalog is a later input interface; this version does not invent one.

V1 generates constant-price four-week candidates, with four explicit weekly price/ad conditions. It compares recorded-sales scenarios under independent series assumptions. It does not estimate causal effects, latent unconstrained demand, substitutions, realized revenue/profit, or business uplift. A successful demand forecaster does not automatically qualify as a price-response model. A valid all-hold plan is useful output, not an engine failure.

## Versioned JSON boundaries

Use [JSON Schema 2020-12](https://json-schema.org/draft/2020-12/json-schema-core) for the later machine schemas. Each object has its exact `schema` discriminator, rejects unknown properties, and requires the fields below unless marked `?`. `Ref` is the backend's immutable `{id,sha256,bytes,media_type,schema_version}`; references must resolve within the authorized workspace or curated sample. SHA-256 values are 64 lowercase hexadecimal characters. IDs are bounded opaque strings. Arrays have declared size limits and unique keys; duplicate/conflicting effective records are errors, never last-write-wins.

| Schema | Required logical shape |
|---|---|
| `pricing-request-v1` | `{schema,plan_id,revision,snapshot_ref,bundle_ref?,scope_ref,origin,period:[int,int,int,int],business_ref,rules_ref,objective:"scenario_contribution"\|"feasibility_only",exclusions?}`; period must be origin+1…origin+4 and scope must match the snapshot. Exclusions are explicit `{series_id,reason,actor}` entries in a new revision; each excluded row remains in coverage and has no executable selection. |
| `pricing-business-v1` | `{schema,snapshot_ref,value_space,records:[BusinessRecord],ad_plan:[AdRecord],receipt_basis,inventory_policy}`; bounds: ≤300 series × four weeks per record kind. |
| `pricing-rules-v1` | `{schema,version,price_tick,minimum_price?,maximum_price?,maximum_decrease_bps?,maximum_increase_bps?,minimum_margin?,maximum_reference_age_weeks,max_changed_series?,inventory_required,manual_candidates?,cost_rule_series?}`; each bounded rule is `{value,unit,provenance,series_ids:null\|[IDs],weeks:null\|[target weeks]}`. Tick covers the whole scope/period. Manual and cost-rule requests are explicit, reasoned analyst decisions, at most one per series. |
| `pricing-candidate-v1` | `{schema,id,series_id,kind:"hold"\|"grid"\|"manual"\|"rule",schedule:[4 weekly conditions],hard_feasible,hard_reasons,model_pricing_supported,support_reasons,forecast_ref?,objective_value?,objective_status}`. |
| `pricing-comparison-v1` | `{schema,request_ref,input_hashes,scope_ref,period,rows_ref,candidates_ref,summary,solver_status,selection_complete,publication_ready:false}`; complete scope is independent of successful pricing coverage. |
| `pricing-row-v1` | `{schema,series_id,item_id,site_id,reference_price,reference_week,reference_age,disposition,reason_codes,strategy,forecast_status,candidate_ids,selected_candidate_id?,hold_candidate_id?,qualification_ref?,coverage}`. |

`BusinessRecord = {series_id,kind,week_index,value,provenance,source_ref,known_at_index,unit,value_space_id}`. Kinds are `unit_variable_cost`, `feature_spend`, `opening_stock`, and `replenishment`; opening stock is at origin, other records identify target weeks. `AdRecord` has the same provenance/source/known-at fields plus `series_id,week_index,feature_ad:0|1|null`. Values explicitly distinguish `observed`, `derived`, `scenario`, and `missing`; missing requires null and a reason. Derived records bind their formula and input hashes. Scenario records bind the actor and named assumption version; a future commitment is a known plan/scenario, never an observed future outcome.

Explicit authored prices (including manual candidates), costs, ticks, margins and spend are finite decimal strings with ≤18 significant digits and ≤8 fractional digits; price/tick >0, costs/spend/stock/replenishment ≥0, margin in [0,1). Observed reference prices and exact hold schedules instead preserve the canonical source float's round-trip precision, which may exceed eight fractional digits for weighted weekly values. Never round that reference to satisfy a rule: a mandatory tick can make its hold infeasible, but the precision is not an ingestion error. Model predictions remain finite nonnegative binary64 values serialized losslessly; do not round source sales to integers. Rule arithmetic uses decimal values; model calls use checked finite float conversions, and returned support flags must still pass. [Decimal arithmetic](https://docs.python.org/3/library/decimal.html).

## Input compatibility, timing and provenance

- All observed/derived history must satisfy observation time ≤origin and known-at ≤origin. Future cost/ad/replenishment records must explicitly identify a plan known at the origin, or a newly authored scenario. Newly authored assumptions never become historical information in a replay; its history/data cutoff remains fixed. Each effective series/week needs one resolved record per applicable kind, including an explicit zero where intended.
- For ordinary uploads, `value_space` binds the exact asserted currency, quantity unit, price basis and net-receipt convention. Cost is per that quantity unit; stock/replenishment and predicted sales use that same unit; spend uses the compatible value unit. No implicit FX, packaging conversion, source merge, or tax/discount assumption. An incompatible or unknown conversion blocks the affected objective/rule instead of producing an amount.
- OJ has no verified currency or package mapping. Its `value_space` uses `{kind:"source_scale",currency:null,source_id,snapshot_ref,quantity_unit:"source_units",price_unit:"source_price_units",mapping_provenance:"scenario"}`. Contribution requires an explicit scenario assertion pairing one source price unit per source sales unit; this is a source-scale index, not dollars or audited money. Label **Estimated contribution · scenario · source-scale units**. Do not combine it with currency-denominated amounts.
- `receipt_basis` must explicitly establish that each candidate price is the unit net receipt used in the objective. A list price without a compatible net-receipt mapping supports price/forecast inspection only. Discounts, coupons, returns accounting, or additional promotional mechanisms are unsupported in v1; reject those requested controls rather than subtracting a discount twice or silently ignoring it.
- Missing cost makes `scenario_contribution` unavailable; `feasibility_only` still returns full scope, hold/manual/rule dispositions and any valid forecasts. A required margin rule with missing cost is unevaluable, not passed. Example cost=60% of the frozen reference price, margin=20%, ±5% change and max changes=20 are optional explicit teaching assumptions, never default facts. The analyst's “Use example business assumptions” action also explicitly accepts the hypothetical source-unit mapping; freeze formula, resulting values and units before comparison. This enables actionable scenario comparisons wherever actual reviewed support and constraints permit a change; no positive gain is guaranteed.
- The ad plan is fixed across all price candidates, with four explicit `0/1/null` values per series. Carrying the last observed ad state forward is a named scenario; null remains unknown. Ad is feature advertising only. No automatic promotion calendar or ad-budget optimization is offered. Four weekly `feature_spend` values, including explicit zeros, are required for contribution; cost and spend remain separate.
- Stock missing means `inventory_check:"not_checked"`, not unlimited supply. When supplied, opening stock and replenishment are explicit; absent replenishment is unknown until an explicit zero plan is recorded. V1 can check cumulative predicted recorded sales through each week against opening stock plus arrivals available at that week's start. It never truncates predictions into a fabricated stockout-demand model. This conditional check is not a service-level guarantee; `inventory_required=true` makes missing compatible supply/predictions a blocker.

## Portable reviewed model bundle

The local research runner binds absolute paths and immutable governance artifacts; those paths cannot serve as cloud authority. A later trusted exporter may run **only after final independent review of the relevant refit and allowed uses**. It preserves original evidence bytes/hashes and creates a separate portable manifest; it never edits research authorization/terminal flags to appear approved. No public endpoint accepts a model, pickle/joblib file, archive, import path or executable code.

`pricing-model-bundle-v1` contains `schema,bundle_id,source_sha256,dataset_version,snapshot_version,origin,scope_hash,history_ref,protocol_ref,core_code_manifest_ref,dependency_lock_ref,environment_ref,models,qualification_ref?,evaluation_refs,original_evidence_refs,allowed_uses,export_manifest_ref`. Each model entry identifies family/candidate, role (`demand_forecast` or `price_response`), origin, configuration and checkpoint ref (null for a baseline). No price model is a supported bundle state. Every file is addressed by content hash; a trusted promotion record binds the final manifest hash, independent reviewer identity, original run lineage and approved uses. A user-supplied `reviewed:true` is insufficient.

The core code manifest hashes the exact model/data modules and transitive inference imports; the lock/environment captures Python, scikit-learn, NumPy/SciPy, joblib and other inference versions. The cloud image contains those exact importable modules/dependencies; new API/Phase 3 adapters may be added without modifying the approved core. All history, qualifications, configuration, checkpoints and evidence needed for inference resolve from immutable server-owned storage, not an original workstation path. Original path-bound governance evidence is an archived audit record; the trusted export attestation establishes the new portable binding.

Before deserialization, verify the trusted registry's expected manifest hash, every referenced byte hash, origin/source/snapshot/scope, approved use and runtime compatibility. Materialize only allowlisted regular files into a private temporary directory; reject traversal, symlinks, unknown files, excessive sizes and user-selected classes. A hash establishes integrity only after the manifest's provenance is trusted. Joblib/pickle loading can execute code and requires a matching trusted environment; no compatibility claim across dependency versions is made. [Official model-persistence guidance](https://scikit-learn.org/stable/model_persistence.html).

A fresh deployment must verify/load/predict from the bundle with the original research directory absent. The OJ planning bundle must actually be a reviewed origin-160 refit; a selection/confirmation fold checkpoint cannot be relabeled. An OJ bundle cannot price an uploaded dataset just because item IDs happen to match. Operational retraining's unreviewed artifacts remain separate until the accepted operational promotion policy authorizes the needed use. The reviewed reference bundle and normal authenticated analyst/reviewer workflow are the gates; this contract adds no per-comparison manual authorization.

## Candidate construction and support gates

1. Freeze request/input hashes and all scope rows. Reference price is the last observed positive price at the origin, with its actual week/age. A missing/stale reference yields an explicit reason; it is not described as a current list price. Keep the exact hold schedule as a comparator even when hard constraints reject it.
2. Resolve each week's bounds: positive price, contractual min/max, allowed change relative to the frozen reference, and `cost/(1−minimum_margin)` where applicable. Constant-price candidates use their four-week intersection. For model pricing, also intersect the series' origin-history marginal range and every planned known ad stratum's supported range. An empty intersection is a conflict/support failure with each original bound retained; never clamp away the conflict.
3. Require an explicit `price_tick` in the same price units (OJ may use a named 0.01 source-unit teaching assumption). Let `k_min=ceil(lower/tick)`, `k_max=floor(upper/tick)`. Enumerate all integer ticks when there are ≤31; otherwise use the 31 indices `k_min + floor(j*(k_max−k_min)/30)`, j=0…30. Deduplicate by exact price. Add the exact hold and at most one explicit constant-price manual candidate: **≤33 candidates/series**. Hold is never rounded to manufacture feasibility; off-tick holds remain visible and fail a mandatory tick rule.
4. Sparse/unsupported series receive no fabricated model-price grid. They retain hold and, when explicitly requested with compatible inputs, a rule candidate: the lowest tick at/above the declared cost/margin/contract floor, subject to every applicable upper/change bound. A manual candidate needs an analyst reason and passes the same hard constraints. Neither is called a model optimum; lack of historical model support is reported and blocks its model-based gain claim.
5. `model_pricing_supported` is the conjunction of: trusted reviewed compatible bundle allowing price scenarios; globally accepted **price-response Poisson** candidate; exact-origin per-series qualification; actual known series/recent-history support; every week's marginal price support; every week's joint known-ad support; and actual `prediction_status == "fitted_prediction"` with finite nonnegative outputs. The selected demand forecaster, tree, baseline, fallback or `constant_zero` state cannot supply price elasticity. The model API's default false qualification flag must be joined to reviewed evidence, never overwritten optimistically.
6. Preserve protocol thresholds: ≥52 observations, ≥5 prices, max/min ≥1.10; accepted negative bounded response and fold stability; per-series validation no worse than control; current refit response passes. Each ad stratum additionally needs ≥8 observations, ≥3 prices and in-range candidate price. Bind the frozen threshold artifact rather than inventing a second mutable policy. These are engineering support checks, not causal identification or confidence intervals.
7. Every comparison call to the frozen `predict_scenarios` receives the complete origin roster × four weeks. Batch candidate index j using each series' jth candidate or its explicit hold, preserving full keys and recording only the intended candidate result. Never fill missing conditions with invented prices. The fixed ad plan is identical for candidates and hold. Price comparisons use the same reviewed price model on both sides; a separate demand-model forecast is labeled separately.

## Objective, hard constraints and optional change cap

For a supported candidate s and series i, with four explicit weekly predictions q, compatible net receipt p, variable unit cost c and feature spend f, compute **J(i,s) = Σ(t=1…4) [(p(i,s,t)−c(i,t)) × q(i,s,t) − f(i,t)]**. No quantity clipping, annualization, implicit discount or repeated four-week spend is permitted. Fractional q is retained. Missing any required term makes J null with a reason. Margin is `(p−c)/p` per week, not markup and not a substitute for total contribution.

Use deterministic decimal arithmetic at precision 50, converting each finite model value through its round-trip decimal string; record that arithmetic version. This is exact evaluation of the declared formula subject to the recorded model/decimal numeric precision, not an exact economic truth. Choose by unrounded J; exact ties prefer hold, then smaller absolute reference-price change, then lower price, then candidate ID. Display rounding never drives feasibility/selection. A hold outside hard bounds can remain a modeled baseline, but cannot be selected/exported as executable.

Forecast-only or rule/manual candidates without qualified response have `objective_status:"not_supported_for_price_choice"`; they cannot win by reusing a flat baseline forecast as assumed elasticity. Under `feasibility_only`, objectives remain null with `objective_status:"feasibility_only_not_scored"`; prefer a feasible hold, while a requested rule/manual change is an explicit decision requiring review. When no feasible candidate exists, selected candidate is null and every failure reason survives.

`max_changed_series=K`, if supplied, is a hard integer cap over distinct executable series whose four-week schedule differs from reference; holds count zero. V1 supports only this optional portfolio coupling. For a fully scored independent comparison, series with an infeasible hold but feasible required change reserve a slot first; if these exceed K or any required series has no feasible candidate, return `infeasible` without a final catalog selection. Choose each required row's best feasible candidate, then allocate remaining slots by descending **positive** best-candidate-minus-feasible-hold J; deterministic ties use series ID. All remaining rows hold. This is a finite additive selection under the declared cap, not substitution-aware or continuous-market optimization.

Rule/manual changes without comparable J are explicit fixed decisions and consume reserved slots; the engine does not rank their gains. Their own infeasibility or more reserved changes than K is a conflict, never an invitation to drop rows. A caller cannot satisfy the cap by silently omitting problematic series. Fixing inputs or excluding a blocking row from executable scope creates a new revision/recalculation with an explicit coverage reason. Other portfolio budgets, price ladders, substitutions and replenishment optimization return `unsupported_rule`; do not expose inactive controls as enforced.

## Output and proposed pure functions

Disposition is exactly one of `change_proposed`, `hold`, `needs_data`, `rule_conflict`, `needs_judgment`, with separate strategy (`model`, `rule`, `manual`, `hold`) and forecast/fallback status. `solver_status` is `complete`, `infeasible`, `partial`, or `failed`; `selection_complete` is false on timeout/partial/failure. Only a completed supported comparison may say a price has the highest estimated contribution among the feasible candidates tested. Every scope row remains present even if a portfolio choice fails.

Summary records full scope/disposition counts, feasible/model-supported/executable counts, missing/excluded reasons, candidate counts and timings. Scenario-vs-hold totals use the **same intersection of supported series and four weeks**, with denominator and missing coverage; no cost-incompatible or unsupported row silently contributes zero. Group totals by compatible value space; source-scale and currency values never combine. Aggregate recorded-sales units also require compatible units. Missing stock checks and independence assumptions accompany the totals.

| Proposed function (not implemented) | Contract |
|---|---|
| `verify_bundle(manifest_ref, trusted_registry, runtime) -> VerifiedBundle` | Validate trust, content and compatibility before trusted load; no training or review generation. |
| `validate_pricing_inputs(request, snapshot, business, rules) -> FrozenInputs` | Exact schema/unit/time/scope validation, deterministic immutable input hashes, explicit blockers. |
| `generate_candidates(inputs, qualifications) -> CandidateSet` | Full scope, exact hold, bounded deterministic grid/manual/rule candidates, hard/support reasons. |
| `evaluate_candidates(bundle, history, candidates, business) -> CandidateEvidence` | Adapt complete rosters to frozen scenario API; keep actual prediction/support statuses and objective terms. |
| `select_catalog(evidence, rules) -> Selection` | Apply feasibility, supported ranking/ties and optional change cap; never approve or publish. |
| `build_comparison(inputs, evidence, selection) -> Comparison` | Reconcile every row/coverage total; return immutable artifact references with `publication_ready:false`. |

The backend binds comparison hashes to the exact draft revision. Changes require recalculation and invalidate approvals; a human may explicitly reject/exclude unresolved rows, but only approved feasible executable rows enter the private Demo ledger under the [review/publication contract](backend-contract-v1.md). Prediction/support, scientific evidence acceptance, and human price approval remain different states.

## Acceptance before implementation handoff

Phase 2 must supply accepted final evidence and the eligible bundle/qualification policy; no successful result is assumed here. Later tests use synthetic arithmetic fixtures and independently enumerated small candidate/cap cases for missing cost/ad, incompatible units, stale/off-tick hold, empty bounds, mandatory changes exceeding cap, zero gain, ties, mixed rule/model rows, fractional quantities and nonfinite output. Verify same-row/week totals, all 249 dispositions, fallback never priced as qualified, checksum/role/origin failures, and bundle inference without local research paths. No protected source labels or new fitting are needed to specify these tests. Measure bounded comparison time/memory before choosing synchronous API execution versus a durable fixed worker; until validated, mark that capability unavailable.
