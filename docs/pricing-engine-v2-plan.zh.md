## 我建议先确定的产品

使用者是定价分析师/经理。第一版采用**每周批量检查商品目录，制定未来四周价格方案**的工作方式。模型训练、价格重算和价格生效是三个独立动作；不因打开页面或收到一张订单就重新训练。

主线：导入数据 → 检查质量与业务变化 → 分析商品组合 → 训练和检验模型 → 按商品选择可用策略 → 批量计算候选方案 → 审核并生成价格版本 → 回放预测并跟踪后续表现。

“覆盖全商品”定义为：本次时点的每个目录条目都有处理状态，包括建议调价、保持原价、规则建议、缺数据、不可行、待审核。它不意味着每个 SKU 都有可靠的独立模型或必须调整价格。“商品目录”与“库存数量/可售状态”是两张不同的表。

建议先用微软仓库自带 Orange Juice 原始数据把真实价格/促销模型与流程做扎实，再扩展大量商品并增加明确标注的零件业务情景。不能把零售商品改名为零件就称为真实汽车零件项目。第一版的整体链路要完整；高级因果估计、商品替代模型和大型联合优化按证据逐步加入。

## Phase 1 — 数据准备与业务分析

**实现内容**

1. 建立有版本的商品目录、交易事实、周价格/销量面板、促销日历、成本、库存、市场参考价和规则表。每条外部输入记录来源、币种、单位、适用范围、有效期和可获知时间。
2. 主粒度建议 SKU × 门店/渠道 × 周；原数据没有门店时就采用 SKU × 周，不虚构门店字段。基准预测期四周，按周滚动。
3. 区分标价、净成交价、折扣、优惠券补贴、退货；统一包装单位。退货单独统计，不能把负销量塞进 Poisson 模型，也不能默默删除后称为净需求。
4. 展示销售额/销量集中度、长尾、周销量和价格走势、数据缺失、价格变化量、可用历史长度及新旧商品。
5. 目录覆盖按每次历史时点定义；未来才首次出现的商品不得提前进入旧时点模型。保留所有目录记录及排除原因，不仅展示“效果好”的商品。

**因素如何进入系统**

| 因素 | 进入何处 | 必须说明的口径 |
|---|---|---|
| Seasonality、节假日、趋势 | 销量/价格响应模型 | 日历可生成；一年数据不足以证明稳定年度季节性，趋势与年内季节也可能混淆。 |
| Promotion：折扣、陈列、广告、优惠券 | 模型控制、情景输入、促销预算 | 有观测才估计历史效果。价格折扣与实际价格高度相关时不能把同一效应算两遍；计划促销必须在预测时已知。 |
| 成本、最低毛利、合同、调价幅度 | 候选价与硬约束 | 不把加价率与毛利率混淆。无可信成本时不输出“已验证利润最优”。 |
| 库存、缺货、补货时间、积压 | 数据解释、可售量约束、清仓策略 | 没成交不等于零需求；未知库存不默认为充足。库存变化按预测时点可知计划使用。 |
| 竞品、替代品、产品档次 | 可比价参考、价格关系约束；后续交叉响应模型 | 同店其他品牌不自动等于外部竞争报价；相关不等于替代因果关系。 |
| 新品、退市、长尾、客户/渠道 | 策略分组、信息共享、适用规则 | 类别来自可靠元数据；人工补的类别需标注。交易差价可能来自客户组合。 |

**参考模式**：复制 `scripts/prepare_data.py:19–25` 来源/哈希模式；根据所选数据官方字典定义连接键和金额口径；不要复制当前“选 12 个示例”逻辑作为模型样本。

**验收**：能从原始文件复现计数/金额；唯一键及连接基数正确；退货和价格口径可追踪；时间字段可审计；每个因素有 observed / derived / scenario / unavailable 状态。

**防止误用**：不填造促销、成本和库存；不把交易表中的空周直接解释为可售零需求；没有可售证据时只能建模记录到的销售，并展示这一限制。

## Phase 2 — 真正训练模型，并决定哪些结果可信（本地研究已完成）

**实际验收范围**：冻结协议见 [model-protocol-v2.md](model-protocol-v2.md)，当前操作说明见 [runbook](model-runbook-v2.md)。249 条店×品牌序列全部保留；近期均值与 52 周季节基线对照两项 Poisson 配置和一项树配置。选择时点为 140/144/148，确认时点为 152/156，最终按冻结的 `poisson-a01` 在 160 重拟合。确认期 1,890 条共同观测的 MAE 为 7,698.47、WAPE 为 45.49%；这是给定实际价格/广告状态的条件预测误差，不是未知未来条件下的准确率或因果收益。161–164 周的 996 条预测仅为延续末次价格/广告状态的情景；244 条序列通过资格筛查，另五条须保持/规则/人工处理。实际行资格还必须同时满足拟合预测、边际价格与联合价格/广告支持检查。

**完成边界**：V2c 的独立结果、代码质量、反模式及序列化修复审查均已通过。默认模型测试为 31 项中 30 项通过、一项需明确启用既有缓存的序列化回归跳过；授权缓存回归也已单独通过。失败运行和已接触确认数据的事实保留。以下是原研究路线说明，实际实现以冻结协议与最终验收为准；Croston、Double ML、因果弹性、预测区间及线上重训均未实现。下一阶段实现受审模型导出、策略路由和业务约束，不再为完成本阶段新增拟合。

**研究问题**：在逐周、只使用当时可获知信息的验证中，加入商品信息、日历和可用促销字段，是否比简单基线更好地预测未来四周记录销量？哪些商品有足够价格变化支持受限的调价情景分析？这两个问题分开报告。

**实现内容**

1. 基线：近期均值/最近值；历史足够才用季节性朴素预测；长尾增加 Croston 类基线。零销量、无历史、无法建立可比价格等情况有明确状态。
2. 可解释模型：带商品差异、日历和可用促销变量的正则化 Poisson 预测模型。以商品/类别共享价格响应作为第一种研究实现。若加入商品相对类别的系数偏差，必须通过设计矩阵和惩罚项实际估计，不能继续用 `activeWeeks/(activeWeeks+8)` 冒充训练。
3. 非线性候选：树模型作销量预测对照。它即使预测更准，也不因此自动获得决定价格的资格。根据训练期价格覆盖、方向稳定性、数据量和时间验证决定是否允许用于候选价比较。
4. 在有足够控制字段和价格变化的数据上，再评估 Double ML；不作为首版必须贴的标签。不能简单把 `log1p(销量)` 对价格的系数叫弹性，也不能把日常价格相关性直接叫因果效果。
5. 输出每个商品的数据量、支持的价格范围、模型来源、预测误差、响应稳定性和使用状态。长尾优先借用可比类别的真实训练结果，否则保持原价/规则建议/人工判断。

**验证设计（数据审计后冻结具体日期）**

- 所有商品共享历史日期切分。建议连续三次滚动验证、每次四周；另保留最后四至八周作一次最终确认，长度依据数据总跨度冻结。
- 商品选择、类别处理、缩放、缺失处理、特征和超参数只用训练/调参窗口。多步预测中的未来滞后值不能偷偷使用实际未来销量。
- 主要预测指标 MAE；辅助 WAPE 在分母非零时报告，同时报告长尾、常销、新品等分组误差和系统性偏高/偏低。不能只用销量大的商品掩盖长尾问题；零分母明确为不可计算。
- 模型选择规则先写清；复杂模型没有稳定改善时保留基线。价格响应无法识别的商品可以有销量预测，但不开放模型调价。
- 历史回放能验证在实际价格下的预测误差。它不能证明没有实施过的新价格会提高利润；离线情景利润、模拟器结果和真实实验效果分栏展示。
- 第一轮模型配置限定为少量可解释候选；示例上限为 3 个 Poisson 正则化配置、2 个树配置、3 个时间折（共至多 15 个全局候选拟合，另计逐序列基线和一次冻结后重拟合）。最终计数按完整试验清单记录。

**运行约束**：先做有真实预处理与模型的短 smoke，测 CPU/内存/耗时再冻结总预算。建议本地 CPU、至多 4 线程、内存上限不超过 8 GiB 且不超过可用内存的一半；首轮总训练候选预算暂定 30 分钟，实际可行性需测量。超过 10 分钟的运行先补进度/资源监控、失败状态和恢复记录。保存代码、输入、配置、依赖版本、时间切分与模型哈希；不启动新的付费训练。

**参考模式**：按 Phase 0 的 Poisson/树/StatsForecast 官方例子调用；EconML 仅在决定采用且核查 cross-fitting 方案后接入。遵循 model-training-governance 的数据边界、预算、独立结果检查和保留失败运行原则。

**验收**：可从命令和冻结输入重跑；存在实际模型文件与验证预测；每个结果对应训练窗口；坏结果也显示；至少能演示一个“预测可用但弹性不足，不能自动调价”的商品。

**防止误用**：不随机拆散周面板；不为每个稀疏 SKU 强行训练独立模型；不把第三方库导入成功当作完成模型；不以模型自己生成的销量证明自己定价最优。

## Phase 3 — 策略路由、候选价与全商品批处理

**本地验收已完成**：22 项模型包测试、32 项定价测试及独立数学检查通过；249 条序列全部保留，5,566 个候选与 16 项穷举组合用例验证通过。实现包含逐条资格/支持检查、显式业务输入、原价/网格/人工/规则候选、硬约束、调价数量上限及一致分母比较；没有新增拟合。下列原路线中的替代需求、置信区间、促销预算耦合等扩展不因此视为已实现。具体范围以 [Phase 3 交接记录](pricing-phase3-handoff.md) 为准。

**实现内容**

每条策略提供候选价、理由、数据要求、适用范围；统一引擎再比较合法候选。策略不是几个输出价格随意平均。

| 商品情况 | 首版处理 |
|---|---|
| 销量与价格信号足够 | 受历史支持范围限制的需求/毛利情景比较 |
| 长尾、价格变化少 | 有依据的类别共享估计，或成本规则；否则保持/人工审核 |
| 新品 | 可比商品参考与业务规则，明确没有自身历史弹性 |
| 促销 | 折扣/促销计划情景、预算与毛利保护；无真实促销模型时结果标为假设 |
| 积压/退市 | 在确有库存/生命周期输入时启用清仓策略 |
| 成本/合同/竞品约束冲突 | 不可行，展示冲突以及需要谁调整什么输入 |
| 数据不足或无可比单位 | 要求补数据；不能用虚假成本或销量强行出价 |

定价顺序：冻结本次数据/模型/规则版本 → 检查适用策略 → 生成原价和候选价 → 应用合同、毛利、涨跌幅等硬约束 → 在相同预测期和同一目标下比较 → 考虑置信度/情景风险 → 形成建议及待审理由。

建议第一目标为**预计贡献毛利**，仅在成本口径足够时使用。计算要明确单位变动成本、促销额外费用和折扣记账，避免净价里已经扣过的折扣再次扣减。成本仅为情景输入时，全组合利润也只能叫情景估计。增加销量、调价数量和预算护栏，原价始终作为对照；强约束下原价不可行时明确显示。

先完成商品独立候选比较及简单组合约束（例如本轮最多调整多少项、促销预算、产品等级价格顺序）。没有交叉需求模型时，组合收益只是在独立需求假设下汇总，不能称为已解决替代竞争。只有需要跨商品联动时再用 OR-Tools；显式显示求解状态和时间上限。

**参考模式**：复制 `web/engine.mjs:90–117` 的可行性与金额舍入思路，保留 `tests/engine.test.mjs` 的独立穷举对照；需要组合求解时按 OR-Tools 官方 CP-SAT 例子接入。浏览器与 Python 如同时计算，使用同一冻结案例做结果对照，不能维护两套不同规则。

**验收**：目录逐项都有状态；硬约束违规为零；无可行解不输出推荐；原价对照、候选依据和阻止原因可见；决策总数与目录覆盖对账；未经处理的库存字段不会暗中影响结果。

**防止误用**：不把每个 SKU 的独立最优价相加当全局最优；不在历史价格范围之外远距离外推；不把有限网格最优写成真实市场最优。

## Phase 4 — 定价工作台、审核与价格版本

**建议页面**

1. **商品组合首页**：本周哪些商品需处理，按可行动性、数据可靠程度和情景机会排序；显示调价/保持/缺数据/冲突数量。
2. **数据与分析**：真实记录、趋势、缺失、季节/促销关联及字段来源。图表旁用一句大白话解释观察到什么。
3. **模型证据**：基线与候选在同一时间窗下的结果，哪些商品能使用模型，哪些不够可靠。
4. **本周定价运行**：选择预测期和业务限制，批量生成方案；单商品展开当前价、成本、历史、需求情景和生效规则。
5. **审核与发布**：接受/修改/拒绝、修改原因、价格生效日、版本和导出。修改任何输入后旧建议失效。
6. **效果跟踪**：先提供历史预测回放；真实实施后的销售数据日后接入。观察性前后对比、模拟情景、对照实验分开标注。

每一步用一个连贯案例贯穿：发现某类商品毛利/销售异常 → 查看证据 → 比较方案 → 审核 → 生成价格表 → 查看后续预测误差。再增加长尾、新品、促销、库存压力、规则冲突等有明确来源状态的情景。

**本地完整运行方案**：Python 数据/训练/批处理 + FastAPI + SQLite + 网页。SQLite 持久保存 run、proposal、review_event、price_version。先做单人演示工作区；切换角色不是企业身份认证，不称为已实现权限隔离。发布目标为本地 sandbox 价格表/CSV 导出，不连真实 ERP。价格版本只接受已审核建议，支持幂等重试和按版本回退；修改后必须重新审核。

**公开运行方案（用户已选择）**：网页连接真正后台；授权用户可上传 CSV/Parquet、启动固定训练任务、查看进度和结果，审核人员用自己的账号保存决定。公共访问者可浏览已发布样例；上传/训练/审核需要登录与服务端授权。前端可以继续静态托管，但不是单靠 GitHub Pages 运行 Python。

后台分为 Web/API、按需训练 worker、对象存储、持久业务记录、登录与权限五部分。上传先校验格式、字段、大小和行数，只运行我们预设训练代码，不执行上传文件中的脚本。训练通过异步队列/任务运行，网页轮询状态；任务、模型版本、建议和审核都保存，不依赖浏览器 localStorage。

第一批权限为 owner / analyst / reviewer / viewer，由服务端分配。普通用户不能自己给自己升级角色或审批权限；修改方案后审核失效；发布检查版本、状态和审批者。以两个真实账号验证多人流程；仍只发布到 demo 价格台账/下载文件，不连接真实 ERP。

优先评估 Azure Container Apps Consumption API + Jobs、Blob Storage、持久表存储和现有身份提供方，利用已核实的个人 Visual Studio 开发测试订阅；也比较现有 GCP Cloud Run/Jobs + Firestore + Storage。不在可缩零容器本地文件系统上存共享 SQLite。公开动态版不能以本地单人版本代替验收。

英文用于面试演示，中文学习模式沿用现有方向。技术名词和公式放详情，主流程用业务语言；Agent 不是必要依赖。以后若加入，只查询结果、解释依据，不绕过规则或直接写入正式价格。

**参考模式**：复制 `web/app.mjs:195–203` 的旧结果失效机制、`:244–255` 的导出交互；按 FastAPI 请求体和 sqlite3 事务文档实现后端。页面重构时再使用 frontend-design 技能，当前不开始设计实施。

**验收**：从数据到价格版本可以完整走一遍；重启后审核记录仍在；未审核/旧版本建议不能进入 sandbox 价格表；同一发布重试不会重复生效；异常输入有可理解的提示；英中切换、桌面和移动端实际浏览器验证。

**防止误用**：不以 localStorage 声称共享审批；不把角色选择器声称 SSO；不把价格 CSV 导出声称已接通 International/Palantir/ERP。

## Phase 5 — 效果验证与最终交付

**实现内容**

- 对每次历史回放保存当时可获知的数据、模型和规则；还原当时的预测，再与真实记录销量比较。
- 价格方案的预计变化与真实业务结果分开；若引入可控模拟器，保存生成机制并明确它是模拟，不作为真实收益证据。
- 编写真实调价实验方案：随机化单元、对照、替代商品之间的干扰、主指标和护栏、持续时长和停止条件。未实际实验时不展示“已实现利润提升”。
- 保留低销量组、模型失败组、策略回退率、缺数据率、无可行价比例以及人工改价原因，作为迭代依据。
- 交付可运行代码、来源/许可说明、冻结数据样本、训练命令、模型记录、实际验证报告和一段完整演示脚本。简历只能写实际验收通过的部分。

**最终验证清单**

1. 官方 API、实际依赖版本及数据使用范围一致；不存在声称集成但未调用的组件。
2. 原始输入→面板→模型→候选→审核→价格版本可追踪；同一版本可重放。
3. 检查未来数据泄漏、促销/折扣重复计数、零销量、缺货未知、退货、单位/币种不一致、新品及库存不明。
4. 独立小规模穷举校验优化结果；约束冲突、过期价格和未审核发布有真实失败路径测试。
5. 模型时间验证和端到端浏览器流程通过；测得性能后才报告 SKU 处理规模，不把 3,000 项演示称为已验证 400,000 项生产能力。
6. 本地完整功能与公共网页功能明确对照，不把静态训练结果浏览包装为在线训练服务。

**参考模式**：微软使用指南的模型监控流程、现有纯函数独立验证及浏览器测试；模型报告遵守真实训练/验证/模拟/实际业务结果的分级。

## 费用、范围和讨论点

用户已选择公开动态后台。默认采用可缩零 API、按需 CPU 训练和少量持久存储，避免常开 VM/云 SQL/GPU。优先用个人 Azure 开发测试额度，目标新增费用控制在很小范围；不是承诺所有云服务永久免费。当前已完成 Phase 1 数据基础、Phase 2 本地真实训练及 Phase 3 定价引擎的独立验收；尚未部署 V2 或为其创建新云资源。实际最终重拟合用时 10.90 秒、外部 cgroup 内存峰值 429,219,840 字节，均为本地测量，不能替代云端容量或账单验证。

**初步算账（2026-11-17 查询，非账单）**：Azure Container Apps East US 公共零售价 API 显示 CPU active $0.000024/vCPU-second、内存 $0.000003/GiB-second。假设每月训练 100 次，每次 5 分钟、2 vCPU/4 GiB，总用量 60,000 vCPU-second 和 120,000 GiB-second，未抵免费量前训练计算约 **$1.80/月**；Google Cloud Run Jobs Iowa 同规格标价约 **$1.32/月**。这不包含 Web/API、冷启动额外时间、存储、日志、构建、网络和其他旧项目；真实训练时间要测量。

[Azure Consumption 官方免费量](https://azure.microsoft.com/en-us/pricing/details/container-apps/)为每订阅每月 180,000 vCPU-second、360,000 GiB-second 和 200 万请求；[Cloud Run Jobs 定价](https://cloud.google.com/run/pricing)当前免费量是每月 240,000 vCPU-second、450,000 GiB-second，按 billing account 聚合。不可给每个 Demo 重复算一份免费量。Firestore 每项目只有一个免费数据库；新建第二库不能自动套用免费额。

历史个人费用审计保留在公共仓库之外：已核实 Azure Visual Studio Professional 每月 $50 开发测试权益且 spendingLimit=On，但没有核实本周期精确剩余额度；GCP 不共享 Azure credit。保留支出限制，不为了上线移除。默认只允许邀请用户启动训练、单并发、单次超时、每日次数和上传上限，并有训练禁用开关；账单预算提醒不是美元硬上限。存储/认证/日志最终 SKU 和费用需在选定部署路径时补齐，本表不是完整报价。

建议分三个可演示里程碑交付，均属于上述完整路线：

- **A：数据和模型证据**——全目录数据分析、来源矩阵、真实训练和时间验证；先证明模型在什么问题上有用。

- **C：更多商品与联合决策**——Kaggle M5 等大量商品资料、可靠的 Double ML 研究、替代关系和组合优化。
